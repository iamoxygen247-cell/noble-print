# Open defects

Defects found and deliberately **not** fixed. One row per deferred defect with a
measured rate where one exists. When fixed, **move the row to Resolved with the test that pins it** rather than
deleting it, so a future regression on the same input is recognisable. (There is
no sha to record: the project is not under version control yet.)

| # | ID | Defect | Measured rate | Cost today | Fix shape |
|---|----|--------|---------------|------------|-----------|
| 1 | F3-R | **F3 reopened by decision, 2026-09-01.** Poll accepts an optional `printerShareId` that hard-overrides each row's `Printer_Name`. Job ids are per-printer, so when the override names a share the row's job does not live on, the lookup and the cancel both 404, the 404 reads as "already gone", the row is requeued anyway — and the original job prints beside its replacement. | **Zero while one printer is registered**, which is the current deployment: the override equals `Printer_Name` on every row, so nothing diverges. Rises only if a second share is added or the two flows are pointed at different shares. | A duplicate sheet per divergent row per retry boundary. | Two options, neither taken: make the override a *fallback* (used only when `Printer_Name` is empty), or resolve the cancel from the row while keeping the lookup on the override. Contained meanwhile by the `printerOverridden` response counter and a WARNING naming F3 — both 0/absent in a correct single-printer run. |
| 2 | H1 | `FakeGraph` keys print jobs **globally** rather than per printer, so a lookup or cancel addressed to the wrong printer succeeds in the fake and 404s in the real service. | Every test run. | No test can reproduce F3-R's double print, so the hazard above is described but not pinned. | Record the share a job was created on; 404 `_get_job` and `_cancel_job` from any other. Expect `test_the_cancel_uses_the_printer_named_on_the_row` to need re-reading afterwards — it would then pass via the `not_found` path rather than the one it names. |

## Known, accepted behaviours (not defects)

These are consequences of the requirement as written, recorded so nobody
"discovers" them later and treats them as bugs.

| ID | Behaviour | Why it is accepted |
|---|---|---|
| ~~G1~~ | ~~A file stuck at `PRINT_PENDING` past 20 days is excluded by **both** Poll and Resubmit and will never be touched again.~~ | **FIXED 2026-09-01.** Poll now examines every pending row and, past `giveUpDays`, cancels the outstanding job and writes `PRINT_FAILED` with a reason. No row can strand *for age*. The `staleCount`/`staleItems` fields and `test.py stale` are gone with the hole they described. **One row shape still needs a human**: `PRINT_PENDING` with a `Print_JobId` but an empty `Printer_Name` — see G3. |
| UC-9 | If Universal Print purges a finished job before Poll observes it, Poll reads the 404 as a stalled attempt and requeues the document — printing it twice. | Poll cannot distinguish "completed and purged" from "never existed", and guessing would mark documents printed that never printed. Mitigated by keeping Poll's cadence well inside the measured retention window. **The likelihood is unchanged** by moving recovery into Poll — it is set by the 10-minute cadence — but the reprint now lands in minutes instead of 72 h, so there is less time to catch it. |
| G3 | A row with a `Print_JobId` but an empty `Printer_Name` is reported `malformed` on every Poll run and never reaches a terminal status. | Job ids are per-printer, so with no printer the job can be neither read nor cancelled. Writing `PRINT_FAILED` would be a guess about a document that may well have printed. Reported every run rather than silently stranded (the difference from G1), but age alone will never resolve it — a human fixes the column. Pinned by `test_a_row_with_a_job_but_no_printer_is_never_given_a_terminal_status`. |
| G2 | `Printer_Name` holds the printer **share id**, not a display name. | The requirement says to store the printer id in that column. The preflight already reads `displayName`, so switching is a one-line change if wanted. |

## Resolved

| # | ID | Defect | Fixed in |
|---|----|--------|----------|
| 1 | D1 | A replacement job was created without cancelling a `stopped` original, so both would print once the printer was fixed. | Design review, before any code shipped. `universal_print.cancel_job` + `_cancel_outstanding`. **Still live after Resubmit was retired** — Poll's requeue and give-up both cancel first; pinned by `test_a_stalled_job_is_cancelled_before_the_requeue` and `test_the_cancel_uses_the_printer_id_not_the_share_id` in `test_poll.py`. |
| 2 | F1 | Poll capped at 15 jobs and took the oldest first: a requirement violation ("all files") **and** starvation -- long-running jobs held every slot, so newer completed jobs were never marked and aged past the 20-day window into limbo. | Post-implementation review. Poll now checks every job in the window, bounded only by the budget, and reports `uncheckedCount`. `test_poll_checks_more_than_fifteen_pending_jobs`, `test_a_long_running_job_does_not_starve_newer_completed_ones`. |
| 3 | F2 | Resubmit ordered its retry queue by `createdDateTime`, which never changes, so a chronically failing file was re-picked every run and blocked everything newer. | Post-implementation review. `select_least_recently_attempted` orders on `lastModifiedDateTime`; eligibility still uses `createdDateTime` per R16. **Structurally impossible since 2026-09-01**: Poll has no batch cap, so there are no slots to starve. Test retired with the endpoint; reasoning kept at the head of `test_review_findings.py`. |
| 4 | F3 | Resubmit cancelled the old job on the **new** printer when the request overrode the printer. The cancel 404'd, a 404 reads as "already gone", so it reported a clean cancel while the original job stayed alive -- the exact double-print the cancel exists to prevent. | Post-implementation review. `_share_for` resolves the share from `Printer_Name`. **Was structurally impossible 2026-09-01 → 2026-09-01; REOPENED BY DECISION** — Poll now takes an optional `printerShareId` that is a hard override, so the two can diverge again. See the live-risk row below. |
| 5 | F4 | `FakeGraph` dropped `$filter` from its `@odata.nextLink`, so page 2 came back unfiltered. A flaw in the **test harness**: real Graph carries the query forward, so no paging test could have caught a real filter-loss bug. | Post-implementation review. `test_paging_returns_only_rows_matching_the_filter`. |
| 6 | F5 | Poll stamped every completion with the request's start time. With F1's cap removed a run can span 90 s, so dozens of jobs would share one timestamp up to a minute and a half stale. | Post-implementation review. `test_each_completion_is_stamped_when_it_was_observed`. |
| 7 | F6 | Resubmit could process one file twice: its two status queries run at different instants, so a file whose status changed between them appeared in both result sets. | Post-implementation review. De-duplicated by item id. **Structurally impossible since 2026-09-01**: Poll runs one query. Its replacement as the concurrency guard is the eTag-conditioned requeue, `test_poll.py::test_a_lost_etag_skips_the_requeue`. |
| 8 | S1 | The final PATCH -- the one recording `Print_JobId` -- was unguarded. A failure there aborted the whole batch with a 500 **and** left the row at `PRINT_PENDING` with an empty job id, which §5.3 defines as a crashed submission. A document that printed fine would be reprinted: the silent double print the claim-first ordering exists to prevent, reintroduced one line from the end. | Second review. The write is guarded, the batch continues, the item record carries a `warning`, and an ERROR line names the coming duplicate. **Sharpened 2026-09-01**: recovery moved from a 72-hour wait to Poll's first retry boundary, so the duplicate now arrives in roughly ten minutes (Poll's cadence, not the 5-minute boundary). `test_a_lost_job_id_write_does_not_abort_the_batch`, `test_a_lost_job_id_write_is_reported_as_a_duplicate_risk`. |
| 9 | S2 | The "whole-invocation" wall-clock budget started **after** site resolution, the preflight and the status query, so that time was free. A slow query plus a full file loop could overshoot Power Automate's ~120 s connector budget -- and a connector that has given up never receives `remainingReady`, so the flow neither loops nor notifies. | Second review. `Budget(started=started)` anchors it at the request. `test_the_budget_covers_the_whole_invocation_not_just_the_file_loop`, `test_the_budget_is_shared_by_poll_too`. |
| 10 | S3 | An offline printer returned `remainingReady: -1`. Flow A's `Do Until remainingReady = 0` can never be satisfied by -1, so it spun to its iteration cap every recurrence; and because the run is a 200 with `failed = 0`, the notify condition never fired either. An offline printer was **silent**. | Second review. `remainingReady: 0` plus `printerAvailable` on every Submit response, and Flow A's condition now tests it. `test_an_offline_printer_ends_the_loop_rather_than_spinning_it`, `test_an_offline_printer_is_visible_to_the_flow`. |
| 11 | S4 | `GRAPH_TIMEOUT_SECONDS` was in the settings template, in the deploy runbook and in design §6.5 as a tunable -- and **no code read it**. Setting it did nothing, silently. | Second review. `graph_client.resolve_timeout_seconds()`, applied to the authenticated client and both unauthenticated paths. `test_graph_timeout_seconds_is_honoured` and four range cases. |
| 12 | S5 | Poll visited `PRINT_PENDING` rows with an empty `Print_JobId` and counted them in no field: not `checked`, not `uncheckedCount`, not `malformed`. The one state §5.3 tells you to expect was the one the response could not show, and the counts did not add up to the rows in the window. | Second review. The invariant `checked + uncheckedCount == pendingFound` is asserted. `awaitingResubmit` was retired with the endpoint — Poll requeues the crashed row itself, so it lands in `checked` like any other. `test_poll_accounts_for_every_pending_row`. |
