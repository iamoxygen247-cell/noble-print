1. Confirmed design

Recurrence — every 5 minutes └─ Health ├─ unhealthy → Teams placeholder → Terminate └─ healthy ├─ Submit — one request, batch size 5 └─ Status — one request, after the Submit attempt └─ Consolidated Teams placeholder
DecisionConfigured behavior
Flow typeSolution-aware scheduled cloud flow
RecurrenceEvery 5 minutes
OrderHealth → Submit → Status
Health gateDo not call Submit or Status when healthy is false
Submit formatExplicitly send image/pwg-raster
Status printerExplicitly send printerShareId
DigestOutside this specification
Notification destinationPlaceholder until the Microsoft Teams team and channel are selected
Intentional differences from the repository reference.

The reference recommends continuing Status during an unhealthy-printer condition and, when the operations are combined, running Status before Submit. This specification follows the requested behavior instead. Pending rows will not be reconciled while Health is false, and files requeued by Status will wait until the next five-minute run before Submit can pick them up.

Submit capacity.

This design calls Submit once per recurrence with batchSize: 5. At twelve runs per hour, the nominal capacity is 60 submissions per hour. Add a bounded Submit loop only if the observed queue requires more capacity.

2. Security and retry recommendations

2.1 Function-key authentication

  1. Create a dedicated host key named power-automate-invoice-print-flow-key.
  2. Do not use the Azure Functions master key.
  3. Copy the dedicated key into Azure Key Vault as a secret named flow-noble-print-function-key.
  4. Use the Azure Key Vault connector directly in the flow to retrieve flow-noble-print-function-key.
  5. Enable Secure outputs on the Key Vault action.
  6. Send the key in the x-functions-key HTTP header, not in the URL.
  7. Enable Secure outputs on the secret-retrieval action and Secure inputs on every HTTP action.
Recommended header 
x-functions-key: @{body('Get_Function_Key')?['value']}

The HTTP action's Authentication field remains None. Azure Functions performs the authentication using the x-functions-key header.

2.2 Retry and asynchronous settings

ActionRetry policyAsynchronous patternRationale
HealthExponential; 2 retries; 10-second base intervalOffHealth performs no writes and is safe to retry.
SubmitNoneOffSubmit creates print jobs and must not be automatically replayed after an ambiguous timeout.
StatusNoneOffStatus can cancel jobs, requeue files, and write SharePoint state.

The next five-minute recurrence is the controlled retry for Submit and Status. Power Automate outbound synchronous HTTP requests have a 120-second limit; the Function App is designed to return within that boundary.

2.3 Trigger concurrency

Enable trigger concurrency and set the degree of parallelism to 1. This preserves one global Health → Submit → Status sequence. Monitor for waiting runs if an execution lasts longer than five minutes.

Power Automate limitation.

After concurrency is enabled on a trigger, removing it requires deleting and recreating the trigger.

3. Flow-scoped configuration

No Power Platform environment variables are required by this design. The six non-secret configuration values are initialized as literal values inside this flow. The Function key remains outside the flow in Azure Key Vault and is retrieved at run time with the Azure Key Vault connector.

Complete these steps only if a dedicated Function key has not already been created.

4.5 Build the Submit phase

Expression-entry rule for this section
  • When these instructions say to select the blue fx button or the Expression tab, paste only the function, such as concat(...). Do not type a leading @ and do not wrap it in @{ }.
  • The Submit Body is built as one typed object with documented workflow functions: union(...), addProperty(...), and json(...). This avoids raw-JSON quoting problems and preserves numbers and Booleans.
  • When using Filter array → Edit in advanced mode, keep the leading @ required by that advanced-mode field.

A. Add Scope_Submit_Try

Inside the Condition's True branch, add a Scope named Scope_Submit_Try. Inside that scope, add an HTTP action named HTTP_Submit.

Method

POST

URI — select the URI field, select fx, paste this, and select Add:

concat(variables('cfgBaseUrl'), '/api/print/submit')

Headers — recommended key/value entry:

  • Content-Type = application/json
  • Accept = application/json
  • x-functions-key = open Dynamic content and select Value under Get Function Key. Selecting the token avoids manually typing the action's internal name.

  3. Optional debugging aid: if HTTP's Secure inputs setting hides the request in run history, put this same union(...) expression in a Compose action named Compose_Submit_Request_Body immediately before HTTP Submit, then select that Compose action's Outputs token for the HTTP Body. The request contains no secret; the Function key remains only in the secured HTTP action.
Do not paste a JSON object into the fx editor.

The fx editor accepts one workflow expression, not raw JSON or an outer @{ ... } wrapper. The union(...) expression above is the complete Body value.

Why this expression is used.

createObject(...) is not recognized by this Power Automate runtime and caused the shown InvalidTemplate failure. union(...), addProperty(...), and json(...) are documented workflow functions. Each variable is inserted as a value rather than concatenated into JSON text, so quote characters in configuration values cannot break the request object.

C. Add Condition_Status_Issue

@or(
  greater(int(body('Parse_Status')?['failed']), 0),
  greater(int(body('Parse_Status')?['gaveUp']), 0),
  greater(int(body('Parse_Status')?['notFound']), 0),

  equals(body('Parse_Status')?['budgetExhausted'], true),
  not(
    equals(
      add(

        int(body('Parse_Status')?['uncheckedCount'])

)

Printer override guard.

Because the Status request explicitly supplies printerShareId, printerOverridden must remain 0. A higher value means at least one row named a different printer and carries duplicate-print exposure.

7. Go-live checklist

  • The dedicated Azure Functions host key exists and is not the master key.
  • The Function key is stored in Key Vault and retrieved directly by the Azure Key Vault connector.
  • Azure Key Vault and Teams connection references have production owners.
  • The hashed Function App base URL matches the Azure portal.
  • The current Universal Print printer share ID has been verified.
  • The Submit body explicitly sends image/pwg-raster.
  • The Status body explicitly sends printerShareId.
  • Health retry is bounded; Submit and Status retries are disabled.
  • Asynchronous pattern is off on all three HTTP actions.
  • Secure inputs hide the Function key from run history.
  • The Team and Channel placeholders have been replaced.
  • Trigger concurrency is set to one.
  • The dry-run test and one-file live test have passed.
  • printerOverridden equals zero in the Status response.
  • The flow is enabled only after all checks above pass.
